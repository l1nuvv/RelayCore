## What the instrumentation measures

`Vulkan queue submit` surrounds the existing queue call. Submit, wait and
completed values carry their owning timeline, including across backend reloads;
completed values reuse the existing query. No additional completion query,
queue idle, device idle or readback is added to ordinary frames.

Renderer CPU preparation, target allocation, pipeline creation and shader
file/module loading are separate scopes. Native model file reading includes
buffer allocation/zeroing and the read; the following decode scope includes
native format parsing and validation. These are elapsed host intervals, not
disk-only latency or sampled active CPU time. Upload plots record requested
mesh/texture bytes. RmlUi context update/render and ImGui backend recording are
separate. Pending ImGui texture updates are counted before the existing backend
call. `Audio device mix` wraps the same engine read used by miniaudio's desktop
default callback, on the real device thread, only in Tracy builds.

`Renderer::log_memory_usage` explicitly samples the existing VMA heap snapshot,
retained upload staging, pending retirements, material descriptors and actual
render extent/scale. It shares snapshot aggregation with the existing diagnostics
button. Budgets stay outside ordinary timing frames. Driver heap usage includes
other applications; VMA allocation/block counts belong to this allocator.
VMA totals cover targets and uploads but do not isolate driver-owned pipeline
memory or ImGui allocations made outside VMA.

Only `relaycore_containment_memory_profile` links the C++ `new` replacements.
They preserve the CRT allocation/free layout, including aligned allocation;
they count successful executable-local requests and requested bytes. They do
not count C heaps, calls compiled inside DLLs, or allocation stack ownership.
They deliberately provide **no free/live-byte estimate**: C++ objects may cross
DLL ownership boundaries. Process retained/peak memory is reported separately.
Snapshots include background executable allocations occurring within the interval;
the atomic count/byte pair is sampled without stopping those threads.

`allocations.csv` contains consecutive update-start intervals and nested
`DemoGame` delegate callbacks. Delegate render ends before Application calls
`Renderer::finish_scene`; engine UI/presentation are also outside the delegate
callbacks. Therefore `ui_bytes` is not all UI allocations, and residual bytes
cannot automatically be called renderer allocations. Memory snapshots, loading
and transitions are marked separately from steady samples.

## Findings and next measurements

H-008-05's manual 55.434 ms frame is CPU frame **682**, trace interval
**16.718661644–16.774095313 s** in `player-20261015-151057/capture.tracy`.
World rendering contains its 15.461 ms scene fence. UI starts 18.202 ms after
the frame start; RmlUi update/render costs **0.278 ms**, including small geometry
uploads. ImGui render preparation ends around +20.127 ms; the next scene wait
starts +55.063 ms and costs **0.076 ms**. The roughly 35 ms gap is therefore
inside the previously uninstrumented ImGui recording/submission region, not
RmlUi CPU layout or the measured final scene wait. The installed ImGui 1.92.9b
backend calls `vkQueueWaitIdle` when updating a texture. This is a bounded
hypothesis for that historical gap; the old trace cannot retroactively prove
its pending texture state.

The new pilot records pending texture count **1** inside ImGui backend recording
at **27.770739094 s / 20.126 ms** and **44.794889350 s / 13.839 ms**.
This supports the texture-update/queue-idle hypothesis and separates it from
RmlUi's ordinary layout/rendering. Exact driver-call tracing is still needed
to prove which call accounts for every millisecond of the historical gap.

The first new timing capture reproduces the present tail: `timing-1`,
**14.346020874–14.400604579 s**, archive, **54.584 ms**. Present API time is
**35.481 ms**, world update **0.345 ms**, RmlUi update/render **0.300 ms**,
resource preparation **0.136 ms**, all queue-submit scopes together **0.148 ms**.
The scene fence costs **15.500 ms**. Two GPU scenes start at **14.362196986 s**
and **14.381972659 s**, lasting **19.672 / 18.573 ms**. The trace localizes the
CPU delay to present while queued GPU work continues; it does not distinguish
