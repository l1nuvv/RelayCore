# G-014 — локальный optimized baseline, 2026-10-07

Consumer — смешанная native-встреча `pressure_transfer`, не непрерывный проход эпизода. Оптимизаций в G-014 нет; измерения не устанавливают speedup или регрессию от добавленного верстака. Сравнение с прежними моделями G-012 некорректно.

## Сборка и workload

Рабочее дерево поверх `38573b6`, включая текущие source/model edits; Windows 11 Pro 10.0.26200, Ryzen 7 3700X, RAM 31,9 GiB, RTX 4060 Ti, driver 32.0.15.9649 (596.49), Vulkan API 1.4.329 при требовании 1.3. Preset `msvc-relwithdebinfo`, Tracy 0.14.1. Runtime подтверждает validation=false. 1280×720, high DPI off, VSync off, hardware_srgb, HDR/ImGui/shadows on, audio off. Настройки не менялись ради результата.

`relaycore_bench_relay_run --pressure-transfer --profile` сначала выполняет два scripted CPU-маршрута, затем загружает реальные entry/distance/cover/powered saves через DemoGame, по две секунды update/render/UI/present каждый. Последовательность повторяется в том же renderer. Камера стационарна, живой rover продолжает движение; стрельбы от пользовательского ввода в измеряемом отрезке нет. Первый проход — first-use процесса/renderer; второй — новая игровая сессия с повтором состояний. OS file cache и shader cache не очищались. Параллельных сборок/GPU checks во время capture не было.

# Отдельный процесс до запуска workload:

Первоначальный запуск без активного Tracy capture обнаружил max 91,17 мс (`tests/g014-profile.log`). Попытка скрытого окна до него остановилась на presentation и не является baseline; эта опция удалена. Для разбора пика выполнен отдельный capture с действующим swapchain. Его лог — `tests/g014-tracy-run.log`; все числа ниже относятся к нему. Capture длится 17,18 с, содержит 16 455 render frames; файл 20,71 MB. Результат workload: passed.

CSV получены `tracy-csvexport` с `-u -f BenchRelay::`, `-u -f 'Vulkan '`, `-u -f PhysicsWorld` и `-g`. Названия BenchRelay — существующие shared runner zones; этот capture содержит только pressure_transfer. CPU строки с запятыми разобраны справа по шести полям, события сопоставлены с CPU frame/state intervals. Анализ: `build/msvc-relwithdebinfo/g014_analyze.py` и `g014-analysis.json`; CSV `g014-{state-events,vulkan-events,query-events,gpu}.csv`. Percentile — sorted sample с индексом `floor(n*p)`.

В измеряемых кадрах upload и upload-wait events каждого состояния сосредоточены в первом кадре; остальные кадры их не имеют. Upload CPU содержит allocation/preparation/submit, wait измеряет `vkWaitSemaphores`; это не GPU transfer duration и не дополнительные независимые затраты поверх wall frame. Query CPU суммирован по render frame при fixed 120 Hz simulation, поэтому query p50 равен нулю. Scene fence — сумма соответствующих wait zones кадра, а не вся render CPU работа.

Подтверждённый расход — подготовка/ожидание ресурсов на первом игровом кадре каждой новой сессии, особенно first-use renderer. GPU scene и queries в этих видах не объясняют длинный первый кадр. Нет основания вводить navmesh, новый render graph или менять steady-state scene scheduling. Сначала G-015 уменьшает повторный маршрут после смерти; E-018 отдельно может перенести необходимые текущие uploads в подготовку/переход, сохраняя владение и rollback. Before/after этой оптимизации ещё нет; полная H-008 и другой ПК остаются открытыми.
