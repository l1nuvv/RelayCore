## F. Synchronization and frame pacing

Scene-slot timeline/fence waits are nested inside renderer CPU work. A wait
cannot be added to that parent or to GPU duration as independent work. The
scene timeline serializes graphics, RmlUi and presentation copy. The source
retains deliberate waits for resource reuse, readback, ImGui and destruction;
normal frames do not issue `vkDeviceWaitIdle`. This audit does not remove waits.

At observation, GPU Scene frame is 19.122 ms, while the CPU scene-slot wait is
15.563 ms/frame. Present averages only 0.285 ms/frame. The CPU waits for prior
scene/UI/presentation use before reusing a slot; GPU workload, rather than VSync
or an independent wait defect, explains the dominant wait. Removing required
completion waits is not an optimization proposal. Upload backpressure and
UI atlas waits are analyzed separately from settled scene-slot pacing.

## G. Memory, startup and transition latency

Process working set, private bytes, device-wide NVIDIA memory usage and VMA
allocation bytes have different meanings. Tracy's large event buffers are
inside the measured process. Process private bytes do not measure engine heap
allocations/frame, and NVIDIA used memory includes other desktop processes.
VMA allocation bytes do not measure total VRAM residency.

Fresh process starts reuse OS/driver caches. The renderer loads/persists its
normal SDL preference pipeline cache independently of the isolated progress
override; these runs are not cold driver-cache experiments. User settings and
progress are compared by hash, rather than clearing them or the cache.

Controlled-owner-1 process peak private bytes are 4261 MiB and working set
1782 MiB; final sampled private bytes are 4028 MiB. Device-wide NVIDIA memory
peaks at 4342/8188 MiB, temperature at 63°C. GPU utilization reaches 100% with
graphics clocks around 2670 MHz. Capacity exhaustion is not demonstrated.
These short runs do not establish absence of a slow leak; profiler buffering,
driver allocations and caches remain mixed in process counters. VMA heap/budget
snapshots and CPU allocation counts were not collected in this execution.

Initial fixture preparation is 3228.864 ms; later preparations are
821.974–1323.421 ms in controlled-owner-1. They include seed save creation,
default menu scene startup and chapter Continue preparation, so they are not
isolated real-player Continue latency. Warm loading repeatedly uploads scene
resources; this should be separated from first-use asset I/O before proposing
loading changes. Shader reload, actual map/editor transitions and preset-switch
latency were not timed.

First workshop HUD atlas upload costs 35.464 ms, inside a 57.615 ms fixture
frame. Across startup/transitions, atlas upload reaches 40.229 ms, nested upload
wait 39.995 ms. `VulkanRmlRenderer::GenerateTexture` explicitly waits for upload
completion on the graphics queue, including queued scene work. This is a
confirmed first-use serialization consumer, not 40 ms of glyph decoding.

The maximized owner window remains 2560×1411 during resize attempts. Those
states do not prove actual High swapchain resize or DRS transition cost.
Fresh-process, ordinary first-use and loading tails remain visible above;
actual resize/DRS transitions remain an unmeasured gate.

### Implementation and ownership

`GameWorldRuntime::import_level_session` prepares directed authored-point links
after taking ownership of the immutable collision world and enemy definitions.
Each enemy retains sixteen 16-bit known/clear mask pairs and one reusable collider
scratch vector. Static traversal certifies whether each box tested against the
streamed colliders remained inside the segment's conservative probe bounds.
Only certified outcomes, both
clear and blocked, are reused; leaving the bounds makes that edge unknown.
Current start/goal, firing positions and targeting remain live queries. Complete
paths and enemy state are not cached or added to saves. Session import rebuilds
the links; restoring a save keeps the same immutable geometry and clears the
existing transient path as before.

Every reused edge first checks live door/actor bounds against its conservative
movement/ground-probe envelope. A possible intersection runs the original
traversal with current blockers. This also permits a dynamic body to supply
ground where static traversal alone fails; an intersecting body revalidates
cached negative results as well as positive ones.
The existing 0.35-unit probes, collision policy, authored graph, Dijkstra order,
0.5-second replanning cadence, perception and combat rules remain unchanged.

Static links alone left a 19.745 ms worst plan and 34.501 ms combined planning
in one frame. Restricting AABB candidates while repeating full queries on every
contact still left approximately 9.7 ms plans. The final `WorldQuery` view retains
the full static stream and narrows only box candidates for probes inside the
segment bounds. Leaving those bounds selects the full stream; a static contact
that pushes the box outside reruns that axis with the original query. Collider
order, native mesh casts, rays and all live dynamic streams are preserved.
The axis-level candidate view alone still reached 2.90 ms. Reusing moving-box
bounds per axis reduced most plans below 1.9 ms, but one retry plan reached
2.165 ms. The final version additionally reuses certified blocked static edges,
while preserving live validation when dynamic blockers touch their probe bounds.
Moving-box bounds are refreshed after every contact, preserving correction order.
The view borrows the enemy-owned scratch buffer only during that segment check.
This is local candidate selection, without a persistent spatial index or new
navigation subsystem.
