# Анализ времени сборки RelayCore

Дата: 2026-10-09. Разделы ниже фиксируют первоначальный анализ CMake, пресетов, настроек CLion и Ninja-логов. На этапе анализа настройки не менялись и новые сборки не запускались. Последующее внедрение и контрольные замеры описаны в разделе «Результат внедрения» в конце файла.

## Текущая конфигурация после внедрения

`msvc-dev` / **RelayCore — Play** уже используют отдельные `.cpp`, PRIVATE PCH и incremental linking без IPO/Unity. Debug также использует PCH. `msvc-relwithdebinfo` / **RelayCore — Profile** и Release сохраняют Unity/IPO. Локальные A/B-замеры выполнены и приведены в [результате внедрения](#результат-внедрения); рекомендации ниже относятся к исходному анализу до этих изменений. Новые performance claims без нового измерения не следуют из этого отчёта.

Полнота Release 1.4.1 отдельно проверена в [протоколе выпуска](playtests/release-1.4.1.md). Это content/updater и локальный startup gate, а не повтор полного unit/graphics suite; известный unit failure из исходного отчёта этим не закрывается.

## Вывод

Задержка в 40–80 секунд согласуется с существующими логами. Главный подтверждённый дорогой участок в последнем выделенном фрагменте RelWithDebInfo — создание EXE с IPO/LTO. Дополнительную работу создают зависимости демо от утилит обработки ресурсов: изменения общих библиотек могут вызвать перелинковку этих утилит и повторную подготовку ресурсов. Unity Build увеличивает объём перекомпиляции при локальных правках. Изменение широко используемых заголовков тоже затрагивает много объектов.

Пока нельзя утверждать, что именно эта комбинация объясняет каждый наблюдаемый пользователем билд: точная команда его медленной сборки и набор изменённых файлов неизвестны. Логи дают конкретные свидетельства дорогих этапов, но не заменяют контролируемое сравнение настроек.

## Что показали существующие логи

Это эвристика границы запуска: Ninja-лог не хранит полноценные идентификаторы запусков и историю всех команд. Данные относятся к сохранённым сборкам, а не к специально проведённому замеру текущего рабочего дерева.

**Складывать эти времена нельзя:** команды частично выполнялись параллельно. Несколько выходных файлов одной команды, в том числе абсолютные и относительные пути, не считаются отдельной работой. Время создания EXE включает цепочку линковки и POST_BUILD; для doctest-целей также может включать обнаружение тестов. Поэтому 48,914 с нельзя целиком приписать самому `link.exe` без дополнительного замера.

Последний выделенный Debug-фрагмент заканчивается на 8,183 с, создание игрового EXE занимает 1,588 с. Это **не** сравнение скорости Debug и RelWithDebInfo при одинаковой правке: состав работы различается. Тем не менее в обоих деревьях видны одновременно исполняемые команды; предположение о полностью последовательной сборке здесь не подтверждается.

## Подтверждённые настройки и их влияние

### 1. Игровая конфигурация включает IPO/LTO

`CMakePresets.json`: `msvc-relwithdebinfo` включает `RELAYCORE_ENABLE_IPO=ON`, `CMAKE_UNITY_BUILD=ON`, Tracy. Эти значения IPO и Unity подтверждены кешем `build/msvc-relwithdebinfo/CMakeCache.txt`. Сохранённая конфигурация `.run/RelayCore Play.run.xml` запускает `relaycore_demo` именно с `msvc-relwithdebinfo`.

`cmake/RelayCoreOptions.cmake` применяет IPO к engine, game runtime, инструментам и тестовым целям, использующим стандартные настройки. В сгенерированном `build.ninja` подтверждены `/O2`, `/Zi`, `/GL`, `/LTCG`, `/OPT:REF`, `/OPT:ICF`, `/INCREMENTAL:NO`. Это конфигурация с межмодульной оптимизацией и полной линковкой, а не режим минимальной задержки между правкой и запуском.

При `/LTCG` часть компиляции выполняется на этапе линковки. Обычный `/INCREMENTAL` с LTCG несовместим; `/LTCG:INCREMENTAL` — отдельный механизм. Поэтому просто добавить `/INCREMENTAL` недостаточно. [Документация MSVC](https://learn.microsoft.com/en-us/cpp/build/reference/ltcg-link-time-code-generation?view=msvc-170).

**Оценка:** первый кандидат на проверку — оптимизированная сборка для итераций с `/O2`, символами и отключённым IPO на собственных библиотеках и EXE. Отключение IPO только у демо не гарантирует устранения LTCG, если его входные объекты по-прежнему собраны с `/GL`. Влияние на runtime performance нужно измерить; имеющийся профиль для игры не следует молча переопределять.

### 2. Подготовка ресурсов связана с изменениями C++

Цепочка в `src/relaygame/CMakeLists.txt`:

```text
relaycore_demo
  → relaycore_demo_assets
      → shaders
      → model_assets → model_import → engine
      → collision_assets → collision_compile → engine
      → irradiance_assets → irradiance_bake → game runtime → engine
```

`cmake/RelayCoreModelAssets.cmake` задаёт зависимость продуктов от executable импортера; collision products зависят от executable компилятора. `cmake/RelayCoreIrradianceAssets.cmake` делает каждый из трёх probe products зависимым от baker и всего списка `model_products`. Baker связан с `RelayGame::runtime`.

Изменение game runtime может перелинковать baker и запустить bake, даже если правка относится к меню или игровому поведению. Изменение engine может затронуть все три утилиты. Это следует из графа зависимостей; не каждая такая правка обязательно изменяет каждый продукт.

В последнем RelWithDebInfo-фрагменте есть команды для **71 модельного продукта**, трёх probe products и коллизии. Их наличие доказывает выполнение соответствующих команд, но не изменение содержимого всех продуктов. Создание probe products занимает 0,360 / 0,453 / 0,843 с; существенная стоимость этой ветки в данном фрагменте — также создание самих утилит, включая 11,315 с для baker.

**Оценка:** сначала проверить стоимость этих утилит без IPO. Затем, если ветка остаётся дорогой, рассмотреть узкое отделение зависимостей baker от игрового runtime. Удалять зависимости от импортера/компилятора без замены нельзя: это нарушит актуальность продуктов после изменения инструментов.

### 3. Unity Build укрупняет единицу перекомпиляции

В RelWithDebInfo CMake объединяет несколько `.cpp` в один файл. Например, текущий `unity_3_cxx.cxx` включает восемь исходников: обновление мира, session builder, enemy runtime, static props, три файла редактора и player controller. Изменение одного из них требует компиляции всей группы. В логе эта группа занимает 9,480 с.

Unity может помогать при полной сборке за счёт сокращения повторного разбора заголовков. Однако для единичных правок её выигрыш не гарантирован. В проекте уже есть выборочные `SKIP_UNITY_BUILD_INCLUSION`; тестовые цели во многих местах имеют `UNITY_BUILD OFF`.

**Оценка:** после проверки IPO сравнить Unity ON/OFF на одинаковой одиночной правке. Если проблема локализована в часто меняемых файлах, проверить исключение именно этих файлов или меньший размер batch. Не отключать Unity повсеместно без сравнения широкой и локальной пересборки. [Настройка размера batch в CMake](https://cmake.org/cmake/help/latest/prop_tgt/UNITY_BUILD_BATCH_SIZE.html).

### 4. Заголовки имеют широкий радиус пересборки; PCH отсутствует

Чтение базы зависимостей через существующий Ninja (`-t deps`) в RelWithDebInfo показало:

| Заголовок | Записи зависимости объектных файлов |
| --- | ---: |
| `relaycore/world/blockout_level.h` | 64 |
| `relaygame/runtime_model.h` | 34 |
| `relaycore/render/renderer.h` | 16 |
| `relaygame/demo_game.h` | 8 |

Это записи из существующего дерева, включая тесты и Unity-объекты, а не число исходных `.cpp` только демо. Изменение таких заголовков может закономерно вызвать широкую пересборку.

В проверенных CMake-файлах нет `target_precompile_headers`, compiler launcher/cache и настроек job pools. В `compile_commands.json` Debug и RelWithDebInfo не найдены команды PCH (`/Yc`, `/Yu`, `cmake_pch`) или ccache/sccache. Поэтому заголовки повторно разбираются обычным способом либо внутри Unity-групп. Это подтверждённая настройка, но конкретная стоимость разбора ещё не измерена.

**Оценка:** рассматривать локальный `PRIVATE` PCH для стабильных часто используемых заголовков после устранения дорогой линковки. Часто меняемые игровые заголовки в PCH добавлять не следует. Макросы implementation-only файлов вроде miniaudio/VMA требуют отдельной проверки совместимости. [Назначение и ограничения PCH в CMake](https://cmake.org/cmake/help/latest/command/target_precompile_headers.html).

### 5. Ограничение параллелизма обнаружено, но не в активных профилях CLion

Во всех девяти build-пресетах `CMakeUserPresets.json` задано `jobs: 1`. При прямом использовании, например, `demo-relwithdebinfo-local`, это ограничивает число одновременно выполняемых задач.

Однако `.idea/workspace.xml` показывает локальные configure-профили отключёнными, а обычные `msvc-debug` и `msvc-relwithdebinfo` включёнными. В общих build-пресетах `jobs` не задан. Следовательно, **`jobs: 1` нельзя объявить причиной обычного Play в CLion**. Фактический параметр `-j` последнего пользовательского запуска неизвестен.

**Оценка:** проверить команду в окне Build. Настраивать параллелизм по доступной памяти и замерам. Не добавлять `/MP` автоматически: при Ninja отдельные компиляции уже могут выполняться параллельно.

### 6. Синхронизация assets выполняется при каждом запросе цели

`relaycore_demo_assets` — custom target с `COMMAND` без output/stamp, поэтому синхронизация выполняется при каждом запросе этой цели. Скрипт рекурсивно перечисляет assets, проверяет generated manifest, копирует с `ONLY_IF_DIFFERENT`, обновляет manifest и проверяет collision receipts, в том числе SHA-256.

Это постоянная работа даже без C++-изменений, но в проверенных фрагментах она занимает около 0,9–1,2 с. На этих данных она не объясняет минутную задержку. Шейдеры и остальные generated products объявлены через `OUTPUT`/`DEPENDS`, поэтому наличие shader target `ALL` само по себе не означает повторную компиляцию шейдеров при каждой сборке.

Кроме ручного копирования runtime DLL, generated commands содержат vcpkg applocal POST_BUILD. Его отдельная доля не измерена. Уменьшение дублирующей работы стоит рассматривать после измерения, а не удалять staging наугад.

## Приоритет следующего шага

1. Зафиксировать реальную команду медленной сборки: профиль, цель, `-j`, запуск build или workflow. Для работы над демо использовать существующий `demo-relwithdebinfo` / цель `relaycore_demo`, если остальные цели не нужны. `BUILD_TESTING=ON` создаёт тестовые цели, но не заставляет собирать их при явном выборе демо.
2. В отдельной конфигурации сравнить оптимизированную сборку с IPO и без него. Сохранять остальные настройки одинаковыми. Изменение флагов требует первоначальной перекомпиляции; её нельзя выдавать за инкрементальный замер.
3. Проверить четыре сценария: повторная сборка без изменений, правка одного gameplay `.cpp`, правка общего заголовка, правка engine `.cpp`. Записывать общее время, компиляцию, создание EXE, подготовку ресурсов; повторять сравнимые сценарии.
4. Если остаётся дорогая компиляция, сравнить Unity и локальный PCH. Если остаётся дорогая ветка assets, уточнить зависимости утилит. При сохранении IPO отдельно проверить `/LTCG:INCREMENTAL`, не подменяя его обычным incremental linking.

Существующие команды для базового замера в подготовленном MSVC developer environment:

```powershell
cmake --build --preset demo-relwithdebinfo
cmake --build --preset demo-debug
```

Для работы только с ресурсами уже существует цель `relaycore_demo_assets`. Переход на Debug может помочь отладочной итерации, но его FPS не характеризует игровую оптимизированную сборку; это также отмечено в `docs/DEVELOPMENT.md`.

## Что пока не установлено

Не измерены отдельно `link.exe`, PDB, vcpkg applocal и doctest discovery; не выполнен A/B-тест IPO, Unity или PCH. Нет данных о загрузке CPU, давлении на RAM, скорости накопителя и влиянии антивируса. Обращение к `Win32_ComputerSystem` через CIM не было доступно, поэтому отчёт не предлагает конкретное число jobs по аппаратным характеристикам.

Нет основания считать CMake сам по себе главным тормозом, утверждать повторную сборку всех vcpkg-зависимостей, менять dependency baseline или удалять build-каталоги. Конфигурация использует Ninja, отключает C++ module scanning, разделяет engine/game runtime на статические библиотеки и предоставляет узкие build-пресеты — эти механизмы уже помогают ограничивать лишнюю работу.

В рабочем дереве есть многочисленные существующие изменения, включая CMake и RmlUi-интеграцию. Первоначальный анализ относится к прочитанному состоянию; старые generated commands и dependency records могут отставать от части файлов. На этапе анализа единственным добавленным результатом был данный отчёт.

## Результат внедрения

По последующему запросу на исправление добавлен `msvc-dev`, наследующий оптимизированный RelWithDebInfo. Он сохраняет `/O2`, символы и Tracy, отключает IPO/LTO и Unity Build. Engine и game runtime получают отдельные PRIVATE PCH со стабильными заголовками STL, GLM и spdlog; игровые заголовки в них не включены. Miniaudio/VMA implementation units исключены из PCH. PCH включён в Debug и Development, отключён в прежних profiling/Release/ASan presets.

Для RelWithDebInfo без IPO убраны принудительные `/OPT:REF`, `/OPT:ICF`, `/INCREMENTAL:NO` и разрешён incremental linking. Настройка выполняется после определения project options, чтобы работала также при configure без пресета. Generated Development commands проверены: `/GL` и `/LTCG` отсутствуют, `/INCREMENTAL` присутствует. У прежнего `msvc-relwithdebinfo` сохраняются IPO и Unity; Release продолжает использовать полный оптимизирующий link.

Добавлены build presets `demo-dev`, `tests-dev`, `validation-dev`, test presets `test-dev`, `validation-dev` и `demo-dev-workflow`. CLion **RelayCore — Play** использует `msvc-dev` и его runtime assets. Отдельный **RelayCore — Profile** сохраняет прежний IPO-профиль. Локальный Development-профиль включён в `.idea/workspace.xml`; из девяти игнорируемых локальных build presets удалено ограничение `jobs: 1`. Эти локальные настройки не входят в Git.

### Контрольные замеры

Сборки выполнены MSVC/Ninja, с `--parallel 8`, на текущем рабочем дереве. Инкрементальные сценарии инициированы изменением только LastWriteTime исходника/заголовка с последующим восстановлением: содержимое не менялось. Это замер стоимости инвалидированной сборки, а не произвольного изменения логики. Первоначальная компиляция нового дерева, установка зависимостей и первый bake не включены в сравнение.

| Сценарий | Прежний `demo-relwithdebinfo` | Итоговый `demo-dev` |
| --- | ---: | ---: |
| Пересборка после инвалидирования `player_settings.cpp` | 29,912 с | 6,490 / 6,487 с |
| Пересборка после инвалидирования `renderer.h` | 39,136 с | 16,171 с |
| Повторная сборка без изменений | 1,093 с | 0,925 с |

В данных сценариях локальная итерация ускорилась примерно в 4,6 раза, пересборка общего заголовка — в 2,4 раза. Это результаты конкретных запусков, а не обещание для всех правок. Отключение только IPO при сохранении Unity дало промежуточные 12,667 с для игрового файла; итоговый результат включает также PCH, отдельную компиляцию и incremental linking.

Логи и `.time.txt` находятся в `build/build-time-analysis/`: `baseline-gameplay`, `baseline-renderer-header`, `baseline-warmup`, `dev-gameplay-3`, `dev-gameplay-4`, `dev-renderer-header-2`, `dev-noop-2`. Повтор `dev-gameplay-2` исключён: во время него IDE перенастроила CMake. Повторные baseline-сборки с суффиксом `-2` пересеклись с компиляцией проверок и также не использованы для расчёта ускорения. Перед итоговыми Development-замерами пользователь закрыл CLion.

### Границы изменения

Зависимости продуктов от импортера/компилятора/baker и проверки receipts сохранены. Общий заголовок по-прежнему может перелинковать asset tools и запустить 71 команду модельных продуктов: их удаление без сохранения корректной инвалидизации скрывало бы устаревшие ресурсы. В итоговом Development-замере весь сценарий с этой работой занял 16,171 с; дополнительное дробление engine/game библиотек не потребовалось для достигнутого результата.

Синхронизация assets остаётся постоянной работой примерно на секунду. Новый профиль не заменяет профиль измерения FPS: влияние отключения LTO на runtime performance отдельно не измерялось. При первой сборке нового дерева требуется полная компиляция и подготовка ресурсов.

Для локальной проверки использованы существующие vcpkg installations. В cache проверяемых деревьев применялся `VCPKG_MANIFEST_INSTALL=OFF`, чтобы не переустанавливать зависимости; это не добавлено в общие пресеты. ### Локальное ограничение vcpkg

Попытка вернуть `VCPKG_MANIFEST_INSTALL=ON` обнаружила, что общий `E:/Code/vcpkg` не содержал утверждённый commit `a42757564758c60651ebc616d9b000b7b91249ef`. Commit загружен через `git fetch --no-tags origin <commit>`; ветка и рабочее дерево не переключались. Текущая рабочая база versions остаётся старее baseline и не содержит требуемых записей, например RmlUi 6.3 и ImGui 1.92.9. Установка manifest с этой базой не проходит.

Пользователь явно выбрал оставить общий vcpkg как есть. Поэтому Development и Debug локально настроены с `VCPKG_MANIFEST_INSTALL=OFF` и существующими installations; configure/build с ними прошли. Для Development `VCPKG_INSTALLED_DIR` указывает на существующий `build/msvc-relwithdebinfo/vcpkg_installed`, для Debug используется его прежняя installation. Это не отключает компиляцию RelayCore, staging или tests; автоматическое обновление зависимостей в этих cache выключено. При изменении manifest понадобится актуальная рабочая база vcpkg и повторный configure с `VCPKG_MANIFEST_INSTALL=ON`. В общих пресетах установка зависимостей не отключена, `vcpkg.json` и baseline этим патчем не изменены.
