# План фундамента RelayCore

Этот план заменяет прежний порядок «доработать один эпизод → добавить врагов». Версия 0.5 остаётся работающим игровым образцом. Следующая цель — собрать из существующих частей понятный каркас движка и игры, на котором можно сделать несколько разных уровней без копирования кода и ручной правки координат.

RelayCore остаётся небольшим проектом одного разработчика на C++20, SDL3 и OpenGL. Каркас здесь означает устойчивые границы, загрузку контента и повторяемый рабочий процесс. Универсальный движок для любых жанров не является целью.

## Что уже есть

- `Application` владеет окном, рендерером, звуком и игровым делегатом; `EngineServices` даёт доступ к живым подсистемам.
- `GameWorldRuntime` запускает фиксированную симуляцию; `LevelSessionBuilder` подготавливает уровень; `WorldSceneRenderer` строит его изображение.
- Есть TOML-карты, текстурный атлас, материалы, освещение, взаимодействия, задания, сохранения и встроенный редактор.
- Есть модульные, контентные и графические проверки. Они служат защитой при изменении границ модулей.

Главный технический риск — игровое поведение, подготовка уровня, UI и инструменты сейчас часто проходят через один `DemoGame` и соседние runtime-файлы. Расширять их без явного разделения жизненных циклов станет трудно. Это направление работы, а не повод переписать всё разом.

## Границы фундамента

| Область | Ответственность |
| --- | --- |
| Движок | Окно и ввод, время, файлы и ресурсы, камера, отрисовка подготовленной сцены, звук, базовые запросы коллизий, диагностика. Он не знает о предохранителе, заданиях и правилах RelayCore. |
| Игра | Экраны и игровая сессия, игрок, предметы, взаимодействия, задания, переходы между картами, сохранение прохождения и позже бой. Она использует сервисы движка. |
| Контент | Карты, меши, материалы, свет, звук, точки входа и выхода, связи объектов. Ошибки данных видны автору при загрузке. |
| Редактор | Изменяет тот же контент, который затем запускает игра. Сохраняет карту, проверяет связи и позволяет пройти её без отдельной ручной правки TOML. |

Правило для каждого этапа: сначала один рабочий сценарий в существующих модулях, затем ровно то выделение кода, которое этот сценарий действительно требует. Новые зависимости и изменения формата данных принимаются отдельно, с проверкой старых карт.

## Порядок работ

### 0.6 — Жизненный цикл игры и граница движка

**Статус:** реализовано. Целевая Debug-сборка, 69 проверок затронутых модулей и сценарий жизненного цикла на `test_room` и `rc022_reference` прошли. Следующий этап — 0.7.

1. Зафиксировать владельцев состояний: меню, игровая сессия, редактор, сохранение, подготовленная сцена. Убрать повторяющиеся пути запуска и замены уровня.
2. Сделать один проверяемый порядок переходов: запуск → меню → новая игра/продолжение → карта → пауза → меню; отдельно вход в редактор и возврат из пробного запуска.
3. Проверить, какие правила задания и взаимодействия находятся в `src/relaycore/gameplay`. Перенести только доказанную игровую специфику в `src/relaygame`; общие запросы столкновений и ввод оставить в движке.
4. Сохранять и загружать сессию через явную версию данных. Несовместимое сохранение должно объяснять причину и не повреждать текущую игру.

**Готово, когда:** повторный запуск, смена карты, ошибка загрузки и пробный запуск редактора не оставляют старых объектов, захваченной мыши или чужого прогресса. Те же переходы работают на двух существующих тестовых картах без специальных веток по имени карты.

### 0.7 — Ресурсы и сцена

**Статус:** реализовано. OBJ с UV/нормалями, отдельная BMP-текстура, трансформации
экземпляров и независимая коллизия. Кэш ресурсов принадлежит рендереру; сцены
переиспользуют неизменённые файлы и сохраняют старый ресурс при неудачной замене.
Проверены 39 целевых тестов и графический сценарий с баллонами на `test_room` и
`power_restoration`, включая повторную загрузку и ошибки путей. Следующий этап — 0.8.

1. Определить один путь от файла к ресурсу и его экземпляру в сцене: где загрузка, кому принадлежит ресурс, когда он освобождается и как сообщается ошибка. Убрать повторный разбор или создание GPU-ресурсов в обычном кадре там, где он реально происходит.
2. Поддержать статический меш с UV, нормалями, текстурой и трансформацией. Начать с одного формата для готовых моделей; выбор загрузчика сделать после короткого рабочего прототипа. Коллизия задаётся отдельно от видимого меша.
3. Дать карте размещать несколько экземпляров одного меша. Сохранить работающие блоковые стены и материалы: меши дополняют геометрию помещений.
4. Определить, какие данные готовит игра для отрисовки и какие читает рендерер. Рендерер не принимает решения о заданиях, уроне или доступе к двери.

**Готово, когда:** один настоящий некубический объект с собственной текстурой ставится в две разные карты, отображается и перезагружается без дублирования загрузки; отсутствие модели даёт понятную ошибку с путём файла. Это станет основой для мебели, оборудования и будущих персонажей, без подмены материалов случайными текстурами.

### 0.8 — Рабочий процесс создания карт

**Статус:** реализовано. Несколько документов, шаблон комнаты, каталог моделей,
размещение на поверхности, инспектор и связи объектов. Сохранение двух карт,
защита несохранённых правок и возврат из пробного запуска проверены.
Проверка пешего пути работает на высоте старта; лестницы и прыжки проверяются в игре.

1. В редакторе открывать и сохранять несколько карт, не привязывая работу к одному эпизоду. Текущий формат TOML можно оставить внутренним форматом; редактирование должно происходить через интерфейс.
2. Размещать стены, статические меши, двери, кнопки, свет и игровые объёмы по поверхности и привязке к сетке. Их основные параметры доступны в инспекторе.
3. Показывать связи «кнопка → дверь → событие/этап задания» и ошибки вроде отсутствующей цели, закрытого обязательного прохода или недоступной точки выхода.
4. Проверить цикл «правка → сохранение → пробный запуск → возврат к правке» без потери несохранённого документа и без записи пробного прогресса в сохранение игрока.

**Готово, когда:** небольшое помещение с текстурированными стенами, моделью, дверью, светом и выходом собирается в редакторе, сохраняется и запускается без ручного вычисления координат или правки TOML.

### 0.9 — Каркас прохождения нескольких карт

**Статус:** реализовано. Именованные входы/выходы, перенос состояния игрока,
состояние посещённых карт и сохранение формата 2 с чтением формата 1.
Сценарий «Два сектора» использует существующие типизированные действия
взаимодействий и этапы задания. Переход, продолжение после перезапуска, обратный
переход и сохранность прогресса при ошибке загрузки проверены графическим сценарием.
Для 0.8–0.9 прошли 20 целевых тестов (838 проверок). Следующий этап — 1.0.

1. Описать входы, выходы и порядок карт в данных игры. Переход подготавливает следующую карту, устанавливает игрока в выбранную точку и оставляет ясную ошибку, если подготовка не удалась.
2. Определить, что живёт только на карте, а что переходит вместе с игроком: здоровье, предметы, выполненные задачи и время. Зафиксировать это в формате сохранения и тестах восстановления.
3. Вынести повторяемые игровые реакции в конкретные типы событий и действий: активация устройства, открытие прохода, смена этапа. Не вводить язык сценариев ради одной цепочки.
4. Сделать две маленькие разные карты как проверку повторного использования: разная планировка и материалы, по одному взаимодействию и переход между ними. Это тестовый контент для каркаса, а не второй большой эпизод.

**Готово, когда:** игрок начинает игру, проходит обе карты, выходит в меню, продолжает после перезапуска и видит прежние предметы и состояние карт. Для второй карты не требуется копировать классы runtime или добавлять ветки по её имени.

### 1.0 — Надёжность и готовность к дальнейшим игровым системам

**Статус:** реализовано. Отдельная копия актуальных исходников без старого
CMake-кэша собрана из пресета `msvc-debug`. Прошли 20 целевых тестов (838
проверок), 13 проверок контента и графический сценарий 0.8–0.9. Захват Tracy
на `msvc-relwithdebinfo` содержит переход, вход в редактор и отрисовку сцены;
в этом коротком сценарии подтверждённой проблемы обычного кадра нет. Команды,
цифры и ограничения: [инструкция разработчика](DEVELOPMENT.md). Запуск
непосредственно из интерфейса CLion остаётся ручной проверкой на машине автора;
профиль и target сверены с текущими CMake presets.

1. Проверить сборку и запуск из чистого checkout через существующие CMake presets и CLion; зафиксировать короткую инструкцию для разработчика.
2. Оставить узкие тесты на загрузку контента, жизненный цикл, переход между картами и сохранение. Графический тест должен показывать важные состояния обеих карт; не запускать полный набор после каждой мелкой правки.
3. Снять один воспроизводимый профиль Tracy на переходе, в редакторе и на обычном кадре. Исправлять только подтверждённые проблемы времени кадра и выделений памяти.
4. После этого выбрать следующую игровую систему по реальной потребности проекта: бой, противник, анимированная модель или более сложное задание. Для анимированной модели отдельно решить загрузку скелета и клипов.

**Готово, когда:** разработчик может создать карту, добавить модель, связать дверь с действием, запустить игру, перейти между картами и восстановить сохранение с понятными ошибками и стабильной сборкой.

## После 1.0 — одна игровая система за версию

| Версия | Результат |
| --- | --- |
| 1.1 — переносимые карты | Папка связанных пользовательских карт переезжает и открывается без правки TOML. Реализовано. |
| 1.2 — подвижный противник | Охранный робот с собственной моделью и текстурой размещается в редакторе, замечает игрока, движется, атакует и сохраняет состояние. Реализовано. |
| 1.3 — законченный бой | Одно существующее оружие получает боезапас, перезарядку, попадания, звук и заметную реакцию цели. Короткая встреча работает после загрузки. |
| 1.4 — движение и анимация | Движение учёного, рука и механические анимации получают видимый ритм. Формат скелета и клипов выбирается только при потребности в гуманоидном NPC. |
| 1.5 — игровая проверка | Небольшой маршрут через несколько карт проходится от старта до финала с контрольной точкой и восстановлением. |

Каждый этап проверяется на двух картах без веток по имени уровня.

## Что откладывается

Прежний этап 0.4 с оружием и врагами больше не стоит перед фундаментом. Существующие боевые заготовки остаются рабочими, но новый подвижный враг и полноценный набор оружия планируются после 1.0. Сетевой режим, ECS, скриптовый язык, render graph, система плагинов и несколько графических API не нужны для описанных проверяемых сценариев.

## Как вести работу

- Одна версия — один законченный сценарий и его критерий готовности. Внутри версии менять границы модулей только там, где это нужно сценарию.
- Не смешивать миграцию формата, графическую полировку и рефакторинг владельцев состояний в одном изменении.
- Перед завершением версии запускать ближайшие проверки и один сквозной сценарий; полный прогон оставлять для изменений, пересекающих несколько подсистем.
- Этот документ задаёт порядок. [Прежний план](ROADMAP.md) сохранён как архив идей для будущего игрового наполнения.
